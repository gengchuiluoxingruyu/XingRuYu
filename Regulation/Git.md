# 提交规范

`git log` 是给未来的自己看的：哪次加了什么、哪次动了配置，一眼看得出来，不必点开 diff。

> [!info] 三条前提
> - **这是笔记库不是代码库**：描述用中文，只有 `type` 前缀用英文。
> - **粒度比格式更重要**：一次提交只做一件事，比写得多漂亮都管用。
> - **模板照着抄就行**：下面的格式与例子直接套用，不必背。

## 1. 格式

```
type(scope): 描述
```

| 部分 | 要求 |
| --- | --- |
| `type` | 必填，只能取 [[#2. type 取值]] 表内的值，小写英文 |
| `scope` | 选填，写明影响的区域，如 `copilot`、`regulation`、`daily` |
| `描述` | 必填，中文，动词开头，不加句号，不超过 25 个汉字（约 50 字符） |

> [!example] 合格
> ```
> add: 添加 2026-11-16 日记
> config: 清理 types.json 中的废弃属性
> add(regulation): 新增标签使用规范
> move: 属性说明移入 Regulation
> ```

> [!warning] 不合格
> | 写法 | 问题 |
> | --- | --- |
> | `修改了文件` | 没说改了什么，等于没写 |
> | `fix: 修复了一个小问题吧。` | 描述含糊、带句号 |
> | `Add: 添加日记` | `type` 必须小写 |
> | `添加日记` | 缺 `type` 前缀 |
> | `update: 改了一些东西，顺便整理了下配置，还删了两篇旧笔记` | 三件事挤进一次提交 |

## 2. type 取值

| type | 用于 | 例子 |
| --- | --- | --- |
| `add` | 新增笔记、剪藏、模板、素材 | `add: 添加 Git 提交规范` |
| `update` | 修改已有笔记的内容或属性 | `update: 补充属性说明中的示例` |
| `fix` | 修正错误：错别字、坏链接、错误属性值 | `fix: 修复 Properties 的失效链接` |
| `move` | 移动、重命名、调整目录结构 | `move: 剪藏统一移入 Row` |
| `remove` | 删除笔记或文件 | `remove: 删除重复的剪藏` |
| `config` | 配置变更：插件、主题、`.obsidian`、`AGENTS.md`、规范文档 | `config: 更新 copilot 技能配置` |
| `style` | 只调格式，不改内容 | `style: 统一各篇的标题层级` |
| `revert` | 撤销某次提交 | `revert: 撤销 c549bdb` |
| `chore` | 自动备份、工具产生的杂项提交 | `chore: vault backup` |

新增 `type` 前先想清楚是否真有必要，宁可归到现有的类里。

## 3. 粒度

| 情形 | 做法 |
| --- | --- |
| 改内容 / 动配置 | 分开提交 |
| 新增 / 删除 | 分开提交（同一次整理除外） |
| 批量同类改动 | 可以合并，但描述要写清范围：`add: 添加 11 月前三周日记`，而不是 `add: 添加日记` |
| 同一件事改了几次 | 最后整理成一次干净提交，别留下 `fix: 又改了一下` |

提交前先 `git status`，确认没有意外文件混进来。

## 4. 提交什么、不提交什么

**该提交**：笔记正文、`Template/` 模板、`Regulation/` 规范、`AGENTS.md`、`.obsidian` 中的类型配置（如 `types.json`）

**不提交**：`Cache/` 里的临时脚本与中间产物、`.trash/` 回收站内容、含密钥或个人隐私的配置、系统生成的临时文件

> [!warning] 密钥与隐私
> 提交前扫一眼 diff，确认没有 API key、token 或其他敏感信息。这类东西一旦进了历史，删掉文件也没用。

## 5. 与自动备份的关系

`vault backup` 这类由插件自动生成的提交属于 `chore`，不受 [[#1. 格式]] 约束。但重要的结构性改动（改配置、移目录、删文件）建议手动提交一次，让历史里留下可读的一笔。

## 6. 提交前自检

- [ ] 有 `type` 前缀，且在 [[#2. type 取值]] 表内
- [ ] 描述是中文、动词开头、不加句号、25 字以内
- [ ] 这次提交只做了一件事
- [ ] `git status` 里没有意外文件
- [ ] 没有密钥、隐私或 `Cache/` 临时文件混入

# 分支管理

本库常态是单分支 `main`。分支不承担日常提交，只为一次大改造留退路。

| 分支 | 用途 | 命名 | 生命周期 |
| --- | --- | --- | --- |
| `main` | 全部日常改动；任何时刻打开 Obsidian 都该是可用的 | 固定 | 永久 |
| `big-change/[描述]` | 批量重命名、目录重构、改模板、动 `.obsidian` 配置等一次影响几十个文件的改造 | 小写字母 + 连字符，不超过 5 个词，如 `big-change/split-row` | 合并后删除 |

- **默认不开分支**：单篇笔记的增改删直接提交到 `main`；开分支会把插件备份和手动提交拆到两条线上，反而更容易冲突。
- **开分支前先对齐**：`git switch main` → `git pull` → `git status` 干净。工作区里不该留半成品。
- **一条分支只做一件事**：中途不顺手改别的；每次提交仍按 [[#3. 粒度]] 来，保证每个中间态都能单独回退。
- **合并后删分支**：`git branch -d big-change/split-row`。纯本地改造不必推远程。
- **`main` 禁强推**：`git push -f` 一律不用，回滚见 [[#3. 回滚]]。

# 工作流程

## 1. 日常改动

```bash
git status                      # 先看有无意外文件
git add Template/Properties.md  # 只加这次动的
git commit -m "update: 补充属性说明中的示例"
git push origin main
```

提交信息按 [[#1. 格式]] 写，取值见 [[#2. type 取值]]；同类改动攒成一条提交，别改一个字推一次。

## 2. 大改造

| 步骤 | 做什么 |
| --- | --- |
| 开分支 | `git switch -c big-change/split-row`，记下起点 `git rev-parse --short HEAD`；不满意就切回 `main` 整个丢掉 |
| 分步提交 | 按「改名一批 → 修链接 → 补索引」拆成几条，条条读得懂、条条能单独 revert |
| 自检 | 链接是否成批失效、属性值是否越界、Bases 查询是否空结果；三项没清干净不合回 `main` |
| 合并 | `git switch main && git merge --ff-only big-change/split-row`；`main` 已前进就先在分支上 `git rebase main` |
| 收尾 | `git push origin main`、删分支；值得留档再打里程碑标签，见 [[#2. 版本与标签]] |

## 3. 自动备份与手动提交

- 插件生成的 `chore: vault backup` 照常跑，不拦不管。
- 要留可读历史，等备份跑完、工作区干净，再手动整理一条：`move: 剪藏统一移入 Row`。
- 一条提交里不同时出现正文改动和备份产物；分不清就先 `git status`。

# 冲突处理

## 1. 减少冲突

- **一次只动一处**：改正文就别顺手动 `.obsidian`。
- **跨设备先拉**：动手前 `git pull`；两台机器不同时改同一篇，也不在两边同时开改造分支。

高频文件冲突了不必犹豫：

| 文件 | 内容 | 冲突时 |
| --- | --- | --- |
| `workspace.json`、`workspace-mobile.json` | 窗口布局 | 留哪边都行，可整块取当前设备 |
| `types.json` | 属性类型定义 | 逐项合并，尽量只在一台机器上改 |

## 2. 解决步骤

1. `git status` 找出冲突文件；正文里会留下 `<<<<<<<` / `=======` / `>>>>>>>` 三段标记。
2. 判断两侧改了什么。正文冲突通常两边都是内容，**合成一段都留下**，不要挑一边整块覆盖。
3. 删掉三行标记，通读一遍前后是否接得上。
4. `git add <文件>`，然后 `git rebase --continue` 或 `git commit`。
5. `git diff` 再确认没丢段落，回 Obsidian 看未解析链接有没有成批冒出来。

## 3. 原则

- 以「内容完整」为准，不以「哪边更新」为准。
- 拿不准先存一份 `.bak` 到 `Cache/`，改完确认再删，规则见 [[TempFiles]]。
- 纠缠不清就 `git merge --abort` / `git rebase --abort` 回到干净状态重来，不在半冲突状态下继续编辑。

# 合并与版本管理

## 1. 合并方式

| 场景 | 做法 | 理由 |
| --- | --- | --- |
| 改造分支 → `main` | `git rebase main` 后 `git merge --ff-only` | 历史保持单线，`git log` 不出分叉 |
| 日常提交 | 直接提交到 `main` | 没有第二条线要合 |
| 撤掉已推送的提交 | `git revert` | 不改写历史，别的设备和备份仓库都对得上 |

不用 merge commit，也不必 `--no-ff` 造合并节点：本库没有多人并行，岔路只会让 `git log` 更难读。

## 2. 版本与标签

- **不打 `vX.Y.Z`**：这里没有可发布物，版本号只会变成占位符。
- **用里程碑标签**标记一次大整理完成，如 `v2026.11`、`v2026.12`，只打在 `main`：

```bash
git tag -a v2026.11 -m "2026-11：规范体系成型，剪藏统一归入 Row"
git push origin v2026.11
```

- **只增不改**：打错了新建一个说明情况，不删不挪。

## 3. 回滚

| 情形 | 做法 | 说明 |
| --- | --- | --- |
| 已推送 | `git revert <hash>` | 再补一条提交说明为什么撤 |
| 未推送 | `git commit --amend` | 并进上一条，或 `git reset --soft HEAD~1` 重新组织 |
| 放弃整次改造 | 未合并：`git branch -D`；已合并：逐条 `git revert` | 不要 `reset --hard`，那会把之后的笔记一起抹掉 |

## 4. 收尾自检

- [ ] `git status` 干净，没有遗漏的改动
- [ ] 改造分支已删，`main` 之外没有残留的活分支
- [ ] 标签只打在 `main`，一次改造只留一个，说明写清范围
- [ ] 合回后打开 Obsidian，未解析链接没有成批增加
