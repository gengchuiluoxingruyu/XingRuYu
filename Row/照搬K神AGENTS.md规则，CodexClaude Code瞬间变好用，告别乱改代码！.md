相信经常用 Codex、Claude Code 写代码、改 Bug 的小伙伴，都踩过同款大坑： 明明只是让AI修复一个小问题，结果它不仅改了目标Bug，还擅自重构整个模块、删减原有注释，把几十行就能实现的简单逻辑，强行封装成多层复杂结构。看着面目全非的代码，实在让人无奈又头疼。

不止我们有这样的困扰，AI领域知名大佬 **[Andrej Karpathy](https://zhida.zhihu.com/search?content_id=276916082&content_type=Article&match_order=1&q=Andrej+Karpathy&zhida_source=entity) （K神）** 也注意到了当下大模型编码助手的普遍问题。

作为OpenAI创始成员、前 [特斯拉自动驾驶](https://zhida.zhihu.com/search?content_id=276916082&content_type=Article&match_order=1&q=%E7%89%B9%E6%96%AF%E6%8B%89%E8%87%AA%E5%8A%A8%E9%A9%BE%E9%A9%B6&zhida_source=entity) 负责人，如今深耕AI教育的他，在社交平台专门总结了LLM编写代码的三大通病：

1. 擅自主观做假设，全程埋头执行，遇到疑问从不主动沟通；
2. 习惯把简单问题复杂化，少量代码能完成的需求，硬生生堆砌大量冗余代码；
3. 对于理解不透彻的代码、注释随意修改，破坏原有项目结构。

针对这些痛点，K神提炼出 **4条核心 [编码规则](https://zhida.zhihu.com/search?content_id=276916082&content_type=Article&match_order=1&q=%E7%BC%96%E7%A0%81%E8%A7%84%E5%88%99&zhida_source=entity)** ，全文仅65行内容，整理成配置文件就能约束AI行为。

这套规则在不同工具中命名略有区别：在 **Codex** 里命名为 `AGENTS.md` ，在 **Claude Code** 中则是 `CLAUDE.md` ，二者原理完全一致——相当于给AI编码助手立下行为准则，规范它的工作逻辑。

## 一、四大核心规则

![](https://pica.zhimg.com/v2-ea4b6561dc817bf23af2694b5023cdb4_1440w.jpg)

把K神的规则翻译梳理后，逻辑清晰、简单易懂，一共四条核心要求，也是约束AI的关键：

1. **编码前先理清思路** ：遇到不确定的内容主动提问，不要凭空猜测；存在多种解读方向时逐一列出；如果发现有更简洁高效的实现方案，主动提出建议。
2. **坚持简洁优先原则** ：用最少代码实现需求，不为临时一次性功能搭建复杂抽象层，不必为极低概率的场景编写容错逻辑；冗余代码及时精简。
3. **只修改必要内容** ：绝不顺手重构运行正常的代码，不改动无关代码与原有注释；发现无效代码可以标注提醒，不要直接删除。
4. **以目标为导向执行** ：先明确任务完成标准，再着手操作；修复、新增、重构类任务，优先设计验证方案，循环自检直至达标。

## 二、完整版规则文本

结合实际使用场景，我把规则优化为 **程序员专业版** 和 **通用简易版** 两大版本，大家根据自身需求直接复制粘贴即可，内容精心整理，建议 **点赞+收藏** ，下次配置直接取用。

### 版本1：程序员版（专业开发场景，适配Codex / Claude Code）

适合日常项目开发、代码调试、工程重构等场景，规则严谨贴合开发规范。

```bash
## 编码前思考
- 明确假设，不确定时询问而非猜测。
- 存在歧义时，列出多种解释，不默默选定单一方案。
- 如果任务有明显更简单的做法，直接指出优化思路。
- 发现代码矛盾、逻辑不一致时及时暂停，请求信息澄清。

## 简洁优先
- 用最少的代码解决问题，拒绝冗余实现。
- 不为一次性需求创建抽象层、复杂架构。
- 不盲目增加扩展性、可配置性，应对“未来可能用到”的场景。
- 若代码可大幅精简，主动重写优化。
- 校验标准：以资深工程师视角判断，代码若过于复杂，立即简化。

## 精准修改
- 仅修改与当前任务直接相关的代码内容。
- 不顺手优化相邻代码、注释、排版格式。
- 不重构原本可以正常运行的代码模块。
- 严格匹配项目现有代码风格，保留原有编码习惯。
- 因本次修改产生的无效导入、废弃变量，可直接删除。
- 发现项目中原有的死代码、冗余内容，仅做文字提醒，不擅自删除。

## 目标驱动执行
- 执行任务前，定义清晰、可落地的成功标准。
- 将“修复Bug”转化为：编写用例复现问题，再调试至用例正常通过。
- 将“新增校验功能”转化为：针对异常输入编写测试用例，保证全部通过。
- 将“代码重构”转化为：完成重构后，确保原有所有测试用例正常运行。
- 多步骤复杂任务，先输出简短执行计划，同时标注每一步的验证方式。
```

### 版本2：通用版

做了去技术化处理，除代码编写外，文案整理、内容编辑、事务处理等场景也能使用。

```bash
## 先想清楚再动手
- 遇到不确定的内容主动询问，不要主观猜测。
- 同一内容存在多种解读方向时，逐条罗列说明。
- 发现更简单高效的处理方式，主动提出建议。
- 遇到逻辑矛盾、信息缺失时及时停止，不强行处理。

## 能简单就别复杂
- 采用最简方式完成任务，不刻意增加复杂度。
- 不为“后续可能使用”额外叠加多余功能与流程。
- 内容、流程明显啰嗦冗余时，及时精简优化。

## 只改该改的内容
- 仅处理和当前任务直接相关的部分。
- 不擅自改动周边无关内容、原有格式与备注。
- 发现其他问题可以文字提醒，不要直接修改。

## 定好目标再执行
- 提前明确任务完成标准，界定“做完”的范围。
- 把单纯“执行动作”，升级为“完成动作 + 结果验证”。
- 复杂多步骤任务，先梳理步骤清单，并说明每一步的验收标准。
```

## 三、配置方法

不同工具的配置路径不一样，下面分 Codex、Claude Code 逐一讲解，操作简单，全程两分钟即可完成配置。

### 1\. Codex 配置步骤（全局生效）

打开 Codex 桌面客户端 → 进入 **设置** → 找到 **个性化** → 打开 **自定义指令** ，将上面任意版本规则粘贴到输入框，保存后即可全局生效。

### 2\. Claude Code 配置步骤（分全局/项目两种）

- 全局生效（所有项目统一使用规则）：在路径 `~/.claude/` 目录下，新建文件并命名为 `CLAUDE.md` ，粘贴规则内容保存。
- 单项目生效（仅当前项目使用规则）：进入对应项目 **根目录** ，新建 `CLAUDE.md` 文件，粘贴内容即可。
